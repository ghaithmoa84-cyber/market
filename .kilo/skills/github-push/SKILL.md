# تعليمات رفع الكود إلى GitHub

أنت مساعد مكلف بتنفيذ عملية رفع آمنة وصحيحة لكود المشروع إلى مستودع GitHub البعيد. **لا ترفع تلقائياً أبداً** — انتظر طلب المستخدم الصريح لكل عملية رفع.

## معلومات المستودع

- **المستودع البعيد:** `https://github.com/ghaithmoa84-cyber/market.git`
- **المالك:** `ghaithmoa84-cyber`
- **اسم المشروع:** `market`

## المتطلبات الأساسية

1. **طلب المستخدم:** لا تبدأ أي عملية رفع إلا بعد أن يطلب المستخدم ذلك صراحةً بكلمة مثل "ارفع"، "push"، "اعمل رفع"، أو ما يعادلها.
2. **الفرع الحالي:** تحقق دائماً من الفرع الذي تعمل عليه قبل الرفع عبر `git branch --show-current`.
3. **نظافة الكود:** تأكد من أن الكود يخلو من أي أخطاء وأن الاختبارات إن وُجدت تجتاز بنجاح.
4. **رسالة Commit:** واضحة وموجزة وتعكس التغييرات، وتتبع نمط Conventional Commits.

## خطوات التنفيذ

1. **فحص الحالة:** نفّذ `git status` لعرض الملفات المعدّلة والملفات غير المتتبّعة.
2. **مراجعة الفروق:** اعرض `git diff --stat` لمعرفة ملخص التغييرات، و `git diff` للملفات الحساسة إن لزم.
3. **سحب التغييرات (Pull):** قبل الرفع، اسحب أي تغييرات جديدة من المستودع البعيد لتجنّب التعارضات:
   - `git fetch origin`
   - `git pull --rebase origin <branch>` (حيث `<branch>` هو الفرع الحالي)
   - في حال وجود تعارض، أبلغ المستخدم واطلب التوجيه قبل المتابعة.
4. **إضافة التغييرات:** 
   - `git add <file>` لملفات محددة (مفضّل)، أو
   - `git add .` لإضافة الكل (فقط بعد التحقق من `git status`).
5. **فحص قبل الـ Commit:** تحقق من أن الملفات المُضافة لا تحتوي على:
   - بيانات سرية (`.env`, مفاتيح API, كلمات مرور, توكنات)
   - ملفات كبيرة غير ضرورية (`node_modules`, `dist`, `build`, ملفات ثنائية كبيرة)
   - أي ملف مشمول بـ `.gitignore` يجب تجاهله
6. **إنشاء Commit:** استخدم نمط Conventional Commits:
   ```
   git commit -m "<type>: <description>"
   ```
   الأنواع المسموحة: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `chore`, `build`, `ci`.
   - الوصف بالعربية أو الإنجليزية حسب سياق المشروع.
   - استخدم `git commit -m "title" -m "body"` إن احتجت وصفاً تفصيلياً.
7. **الرفع (Push):** ارفع إلى الفرع الحالي على المستودع البعيد:
   ```
   git push origin <branch>
   ```
   - إن كان الفرع جديداً ولم يُرفع من قبل: `git push -u origin <branch>`.
   - إن فشل الرفع بسبب عدم وجود إذن أو فرع محمي، أبلغ المستخدم.

## معايير الرفع الناجح

- ✅ تم تنفيذ الرفع فقط بعد طلب المستخدم الصريح.
- ✅ لا توجد ملفات سرية أو بيانات اعتماد في الـ commit.
- ✅ رسالة الـ commit تتبع نمط `<type>: <description>`.
- ✅ تم عمل `pull --rebase` قبل الرفع لتجنّب التعارضات.
- ✅ الرفع تم إلى الفرع الصحيح (`origin <current-branch>`).

## القواعد الصارمة

- ⛔ **لا ترفع أبداً بدون إذن صريح من المستخدم.**
- ⛔ **لا تضف أبداً ملفات `.env` أو أي ملف يحوي مفاتيح/كلمات مرور/توكنات.**
- ⛔ **لا ترفع مجلدات ضخمة** مثل `node_modules` أو `dist` إلا إذا كان المستخدم يطلب ذلك صراحة.
- ⛔ **لا تستخدم `git push --force` أو `git push -f` بدون إذن صريح إضافي.**
- ⛔ **لا تعدّل `git config` (global أو local) بدون إذن صريح.**
- ⛔ **لا تتجاوز خطافات ما قبل الالتزام (pre-commit hooks) أو ما قبل الدفع (pre-push hooks) بـ `--no-verify` إلا بإذن صريح.**

## ما يجب فعله عند الفشل

- إذا ظهر تعارض بعد `pull --rebase`: أبلغ المستخدم واطلب التوجيه، لا تحاول حل التعارض بنفسك.
- إذا فشل الرفع بسبب عدم وجود إذن: تحقق من بيانات المصادقة (`gh auth status`) وأبلغ المستخدم.
- إذا اكتشف وجود أسرار مسرّبة في الكود المراد رفعه: **أوقف العملية فوراً** وأبلغ المستخدم قبل أي رفع.
